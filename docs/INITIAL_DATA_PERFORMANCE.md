# 초기 데이터 기동 성능 점검

2026-09-19, 동일 실행 JAR과 매번 새 PostgreSQL 18.6 컨테이너에서 측정했다. 애플리케이션 코드는 변경하지 않았다. Java 실행 요청부터 초기 데이터 완료 로그 관측 및 HTTP 응답 확인까지이며 DB 준비·빌드 시간은 제외한다. OS 캐시·백그라운드 부하를 통제한 벤치마크는 아니다.

## 반복 측정

| 실행 | 기동 관측 시간 | 생성·검증 Runner |
| --- | ---: | ---: |
| 이전 실행 | 80.765초 | 60.100초 |
| 반복 1 | 85.658초 | 65.566초 |
| 반복 2 | 81.300초 | 58.395초 |
| SQL 통계 계측 실행 | 81.071초 | 60.794초 |

일반 실행 3회는 약 81~86초이며 모두 이 환경에서 1분을 초과했다. SQL 계측 실행은 pg_stat_statements를 추가한 별도 실행이므로 동일 조건의 반복 표본과 구분한다. 모든 실행에서 초기 데이터 개수는 10·100·10,000·250·500·500·500·0으로 확인했다.

## 실행 환경 표본

- Windows 호스트: Ryzen 5 3500U, 물리 4코어·논리 8개, OS에서 사용 가능한 전체 물리 메모리 약 9.95GiB.
- 측정 전 여유 메모리 약 903MiB, CPU 순간 부하 5%.
- Docker가 인식한 자원: CPU 8개, 메모리 상한 약 4.78GiB. 실제 사용량을 의미하지 않는다.
- 반복 실행 중 6개 표본: 여유 메모리 366~434MiB, CPU 19~84%, 페이지 읽기 0~252회/초.

메모리 여유가 적고 페이지 읽기가 관측되어 환경 영향이 의심된다. 페이지 읽기에는 파일 기반 페이지도 포함될 수 있으므로 전부 스왑 때문이라고 해석하지 않는다. 메모리를 확보한 비교 실행을 하지 않았으므로 환경 영향의 비율이나 절약 가능한 시간을 단정하지 않는다. 표본 수집 자체의 영향도 분리하지 않았다.

## PostgreSQL에서 확인한 SQL

| SQL 유형 | 실행 횟수 | DB 실행 시간 합계 |
| --- | ---: | ---: |
| 학생 PK로 존재 확인 | 10,000 | 188.791ms |
| 과목 PK로 존재 확인 | 250 | 5.236ms |
| 강의 담당 복합 PK로 존재 확인 | 500 | 11.182ms |
| 학생 INSERT | 10,000 | 1,655.741ms |
| 전체 도메인 INSERT | 11,860 | 개별 SQL 통계로 보관 |
| 18학점 초과 학생 검사 | 1 | 5,608.712ms |
| 시간표 충돌 검사 | 1 | 473.483ms |

총 10,750번의 존재 확인 조회는 모두 결과 0행이었다. 빈 DB에서 처음 생성하는 데이터에 대해 발생한 조회다. 직접 부여한 ID와 새 엔티티 판별 방식이 결합되어 saveAll의 merge 경로를 타는 현재 코드 및 [Spring Data JPA의 저장 동작](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html)과 일치한다.

[pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html)의 전체 SQL total_exec_time 합계는 약 8.476초였다. 이는 DB 내부 실행 통계이며 쿼리 계획·클라이언트 처리·JPA 관리·JVM 작업·통신 시간 등을 모두 포함한 기동 시간과 같지 않다. 이 차이를 전부 네트워크 지연이나 PC 성능으로 돌릴 수 없다. 존재 확인 SELECT의 DB 실행 시간은 짧지만 많은 호출의 전체 왕복 비용은 별도 확인 대상이다.

18학점 검사는 학생 전체에 상관 집계를 수행하는 현재 구현에서 5.609초가 측정됐다. DB 내부 통계상 가장 긴 단일 쿼리였다. 신청 테이블이 비어 있어도 검사를 실행하며, 학생 전체 상관 집계 대신 신청이 있는 학생을 대상으로 집계하는 방식의 검토가 필요하다. 구체적인 실행 계획·JIT 기여도는 이번에 수집하지 않았다.

## 후속 비교 대상

1. 현재 확정된 빈 DB 전용 생성 경로에서 새 엔티티임을 명시하여 불필요한 존재 확인 조회를 줄인다.
2. 학생별 학점 검증을 실제 신청 데이터 중심의 집계로 검토한다.
3. 변경 후 같은 조건에서 SQL 횟수·기동 시간·데이터 정합성을 비교한다. 실행 환경의 기여도를 구분하려면 별도로 메모리 여유를 확보한 동일 코드 비교가 필요하다.

이번 점검에서는 성능 계측 스크립트만 보완했다. 저장 방식과 검증 로직의 변경 효과는 아직 측정하지 않았다.

## 재현

PowerShell 7에서 bootJar로 만든 동일 JAR을 사용한다.

```powershell
./scripts/verify-initial-data.ps1 -FirstOnly
./scripts/verify-initial-data.ps1 -FirstOnly -SqlStats
```

스크립트는 실행마다 임시 DB·계정을 생성하고 자신의 컨테이너와 Java 프로세스만 정리한다. 개발 DB는 사용하지 않는다. 결과는 .tools/seed-check-<실행 ID>/result.json, 계측 시 SQL 통계는 같은 폴더의 sql-stats.json에 저장된다. 컨테이너의 초기 설정용 임시 서버를 준비 완료로 오인하지 않도록 TCP로 pg_isready를 확인한다.

## persist 적용 후 확인 — 2026-09-20

학생·과목·강의 담당의 최초 저장을 persist로 전환했다. 단일 생성 트랜잭션과 마지막 flush·정합성 검증은 유지했다. 자동 ID를 사용하는 학과·교수·강좌·수업 시간 저장은 변경하지 않았다.

동일 SQL 통계 옵션을 사용한 이전 계측 실행과 이번 실행을 비교했다. OS 부하와 메모리 여유를 통제한 A/B 벤치마크는 아니며 각 1회 결과이다.

| 항목 | 변경 전 | 변경 후 |

| 학생·과목·강의 담당 PK 존재 확인 SELECT | 10,750회 | 0회 |
| 전체 도메인 INSERT | 11,860회 | 11,860회 |

대상 SELECT 제거는 SQL 통계로 확인됐다. 생성·검증 구간은 이번 표본에서 짧아졌지만 전체 기동 시간은 거의 같았다. 이번에는 Runner 시작 전 프로세스 실행 경과가 약 40.686초였다. 따라서 전체 기동 개선이나 1분 조건 충족을 주장하지 않는다. 학점 검사 쿼리는 변경하지 않았으며 여전히 후속 개선 대상이다.

초기 데이터 개수 10·100·10,000·250·500·500·500·0과 /health 404를 확인했다. 이번 실행은 FirstOnly 계측으로 재시작 시나리오를 다시 실행한 결과는 아니다.

저장 서비스 5개·Runner 4개 중 첫 실행은 8개 통과, 롤백 테스트 1개는 테스트 더블의 abstract flush 호출 문제로 실패했다. 테스트에서 실제 EntityManager.flush를 호출하도록 고친 뒤 실패한 1개를 재실행하여 통과했다. 관련 9개 시나리오를 확인했으며 전체 테스트 모음을 재실행한 결과는 아니다. 생성 데이터 전체 커밋과 실제 INSERT 후 예외·최종 검증 실패에 대한 전체 롤백을 확인했다.
## 추가 반복 측정과 학점 검증 개선 — 2026-09-20

persist 적용 JAR을 변경하지 않고 최초 기동을 세 번 더 순차 실행했다. 매번 빈 PostgreSQL 컨테이너를 사용했고 이 세 실행에는 SQL 통계를 켜지 않았다.

전체 기동은 70.857~87.290초로 편차가 있었고 세 실행 모두 1분을 초과했다. 실제 데이터 개수는 모두 유지됐다. 이 편차 때문에 단일 전체 기동 시간 차이를 코드 변경의 효과로 단정하지 않는다.

이후 countOverCreditStudents를 학생마다 수행하는 상관 합계에서, 대상 연도·학기의 신청을 학생별 GROUP BY/HAVING으로 묶어 18학점을 넘는 학번을 구하고 해당 학생 수를 세는 JPQL로 변경했다. 반환형·18학점 기준·예외 처리는 유지했다. IN 하위 쿼리를 사용하여 엔티티 모델과 기존 Spring Data JPA @Query를 유지하며 새 스키마·라이브러리·native SQL을 추가하지 않았다. [Spring Data JPA 쿼리 선언](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html)을 따른다.

- /health는 404이며 전체 서비스 준비 및 1분 조건 충족으로 간주하지 않는다.

학점 검사 실행 시간은 초기 신청 0건인 상태의 단일 계측 비교이다. 신청 데이터가 많은 재시작의 성능이나 모든 환경의 개선율을 보장하지 않는다. 전체 기동의 편차와 DB 내부 실행 시간을 구분한다.

검증: EnrollmentRepositoryTest 20개, InitialDataValidatorTest 19개, InitialDataServiceTest의 데이터 정합성 시나리오 1개, 총 **40개 통과**, 실패·오류·건너뜀 0. 신청 없음, 17·18·19·21학점 경계, 여러 초과 학생의 정확한 인원 수, 연도·학기 분리, 기존 관계·신청 검증을 확인했다. bootJar 빌드도 성공했다. 전체 테스트 모음을 재실행한 결과는 아니다.

동일 실행의 PostgreSQL 내부 통계는 학생 INSERT 10,000회 합계 2.049초, 강좌 INSERT 500회 합계 0.180초, 시간표 충돌 검사 0.583초, 동일 과목 검사 0.235초, 전체 SQL 실행 시간 합계 3.514초였다. DB 내부 실행 시간과 애플리케이션 경과 시간은 측정 범위가 다르므로 더하거나 그 차이를 단일 원인으로 단정하지 않는다.

우선 확인 대상은 다수의 INSERT를 수행하는 저장 경로와 별도로 긴 서버 초기화 구간이다. 데이터 검증 전체 1.631초만 줄이는 것으로 전체 1분 기준을 안정적으로 달성한다고 볼 수 없다. 단일 실행 표본이며 초기 신청은 0건이다.
## 초기 생성 INSERT 배치 적용 — 2026-09-20

초기 생성 트랜잭션에서 Hibernate Session의 JDBC batch size를 50으로 설정하고 finally에서 이전 값을 복원한다. 일반 저장의 Hibernate 배치 설정을 전역으로 바꾸지 않는다. PostgreSQL 드라이버에는 Hikari data-source-properties의 reWriteBatchedInserts=true를 설정하여 JDBC 배치에 담긴 INSERT를 다중 VALUES 문장으로 재작성하도록 했다. 드라이버 옵션은 연결 풀 전체에 적용되며 현재 명시적인 배치 활성화 범위는 초기 생성이다.

[Hibernate 세션별 배치 설정](https://docs.jboss.org/hibernate/orm/current/javadocs/org/hibernate/SharedSessionContract.html)과 [pgJDBC 연결 옵션](https://jdbc.postgresql.org/documentation/use/)을 확인했다. 배치 크기 50은 이번 적용값이며 최적값 탐색 결과는 아니다. IDENTITY ID의 학과·교수·강좌·수업 시간 저장 방식과 스키마는 유지한다. 트랜잭션·최종 flush·검증도 유지한다.

| --- | ---: | ---: |
| 전체 최초 기동 관측 | 81.241초 | 48.648초 |
| 초기 데이터 Runner | 43.232초 | 10.185초 |
| 강좌 저장 구간(앞선 대기 INSERT 포함 가능) | 35.106초 | 4.381초 |
| 마지막 flush | 1.519초 | 0.600초 |
| 학생 INSERT DB 문장 실행 횟수 | 10,000회 | 600회 |
| 과목 INSERT DB 문장 실행 횟수 | 250회 | 15회 |
| 강의 담당 INSERT DB 문장 실행 횟수 | 500회 | 30회 |
| 전체 도메인 INSERT DB 문장 실행 횟수 | 11,860회 | 1,755회 |

저장 행 수는 학생 10,000·과목 250·강의 담당 500을 포함해 전체 11,860행으로 유지됐다. DB의 INSERT 문장 실행 횟수는 JDBC 배치 호출 횟수나 네트워크 왕복 횟수와 같지 않다. 드라이버가 배치 내부 문장을 나누어 재작성할 수 있어 batch size 50이 DB의 모든 문장에 정확히 50행씩 들어간다는 뜻은 아니다.

배치 적용 실행의 기타 구간: 해시 0.378초, 학과 0.199초, 교수 0.471초, 학생 persist 등록 0.374초, 과목 persist 등록 0.028초, 수업 시간 1.746초, 강의 담당 persist 등록 0.085초, 최종 검증 1.369초. 모든 값은 단일 실행 표본이며 환경 변동이 통제된 반복 벤치마크는 아니다. 단계별 시간과 엔티티별 DB 실행 시간의 차이는 앞 절의 주의를 적용한다.

검증은 InitialDataServiceTest 7개·InitialDataRunnerTest 4개, 총 11개 통과(실패·오류·건너뜀 0). 학생 배치 앞부분과 뒷부분에 실제 PK 중복(SQLSTATE 23505)을 유발한 두 경우, 저장 후 예외 및 최종 검증 실패 모두 전체 초기 데이터를 롤백함을 확인했다. 전체 테스트 모음을 재실행한 결과는 아니다.

실행 JAR 검증에서는 초기 개수 유지, 초기 비밀번호 없는 재시작, 기존 신청을 포함한 전체 데이터 보존, 수업 시간 누락 시 종료 코드 1 및 데이터 보존을 확인했다. 재시작은 27.164초, 검증 Runner는 1.439초였다. 개발 DB는 사용하지 않았다. 이번 최초 기동 표본은 1분 이내이나 /health는 여전히 404이고 API 전체 준비 조건 충족을 선언하는 결과는 아니다.
