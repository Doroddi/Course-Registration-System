# 신청·취소 동시성 및 신청 순서 설계

상태: 주요 정책 확정·구현 세부 검토 / 구현·성능 측정 미실시

요구사항 D55~D56의 검사 순서, D61의 별도 학생 존재 확인 제외, D62의 취소 학기 제한, D63의 시간표 신청 순서 정렬을 구현하기 위한 설계이다. 학생·강좌 행 잠금, READ COMMITTED, 잠금 후 조회, 인원 COUNT, 증가 신청 ID는 D64~D66으로 확정했다. 취소 잠금 순서·대기 실패 처리·강좌 정보 변경 제한은 D67~D69로 확정했다. 기술 스택은 D73~D74에 따라 Spring Data JPA와 PostgreSQL 18.6으로 확정했다. 잠금은 D75에 따라 JPA 우선 적용 후 FOR NO KEY UPDATE 생성 여부를 확인하고 필요 시 native query로 전환한다. 증가 BIGINT 신청 PK와 학생·강좌 UNIQUE는 D76으로 확정했다. 생성 구문과 인덱스는 후속 검토한다.

## 확정 사항과 구현 제안

| 항목 | 제안 | 목적 |
|---|---|---|
| 동시 요청 제어(확정) | 학생 행 → 개설 강좌 행 순서의 비관적 잠금 | 같은 학생의 학점·시간표·중복과 강좌별 정원을 각각 보호 |
| 잠금 적용 방침(확정) | 두 행 모두 JPA @Lock(PESSIMISTIC_WRITE) 우선 적용. FOR NO KEY UPDATE 생성·동작 확인 후 필요 시 native query 전환(D75) | 서로의 신청 변경은 직렬화하되 외래 키 확인의 KEY SHARE와 불필요한 충돌 완화 |
| 격리 수준(확정) | READ COMMITTED | 잠금을 기다린 뒤 실행하는 조회가 앞선 커밋을 반영 |
| 신청 인원(확정) | ENROLLMENT의 강좌별 COUNT | 초기 구현에서 별도 인원 카운터의 동기화 부담을 피함 |
| 신청 순서(확정) | ENROLLMENT.enrollment_id 증가 ID로 정렬. BIGINT IDENTITY PK는 구현 제안 | 같은 학생의 성공한 신청 저장 순서를 재현 |
| 중복 방어 | UNIQUE(student_number, offering_id) 유지 | 동일 개설 강좌 중복을 DB에서도 방어 |

학생 행 잠금은 존재 확인용 exists 쿼리가 아니라 동시 요청을 직렬화하기 위한 조회이다. 학생 삭제를 고려하지 않는 정책을 유지한다. 학생 행의 프로필 값을 수정할 필요는 없다.

## 신청 흐름

인증과 요청 입력 검증을 통과한 뒤 아래 DB 작업을 한 트랜잭션에서 수행한다.

1. 개설 강좌 존재와 서버 대상 학기를 확인한다. 이 단계에서는 강좌 변경용 행 잠금을 획득하지 않는다.
2. JWT sub에 해당하는 학생 행의 잠금을 획득한다.
3. 잠금을 획득한 뒤 해당 학생의 대상 학기 신청 내역을 읽는다. 학생 잠금 전에 읽은 시간표·학점 결과를 검증에 재사용하지 않는다.
4. 동일 개설 강좌 → 동일 과목 → 최대 학점 → 시간표 충돌 순으로 검사한다. 실패하면 신청을 저장하지 않고 트랜잭션을 종료한다.
5. 개설 강좌 행의 잠금을 획득한다.
6. 잠금 획득이 완료된 뒤 별도 SQL 문으로 해당 강좌의 신청 인원을 COUNT한다. 현재 인원이 정원 이상이면 COURSE_FULL로 거절한다.
7. 신청 행을 INSERT하면서 enrollment_id를 발급한다.
8. 커밋하고 성공 응답을 반환한다. 학생·강좌 잠금은 트랜잭션 종료까지 유지한다.

잠금을 획득하는 SQL과 인원 COUNT를 한 SQL의 서브쿼리·CTE로 합쳐 이전 스냅샷을 읽지 않도록 주의한다. ORM 구현에서도 잠금 전에 로드한 캐시·컬렉션으로 검사를 수행하지 않도록 검증한다.

## 취소 흐름

취소도 학생 조건과 정원 집계의 일관성을 보호하도록 D67의 확정 흐름을 따른다. 인증·경로 입력 검증 후 한 트랜잭션에서 처리한다.

1. 개설 강좌 존재와 대상 학기를 확인한다.
2. 해당 학생 행 잠금을 획득한다.
3. 해당 개설 강좌 행 잠금을 획득한다.
4. 학생·강좌 조합의 ENROLLMENT를 DELETE한다. 삭제 행 수가 0이어도 기존 정책대로 성공이다.
5. 커밋 후 성공 응답을 반환한다.

취소에도 학생 → 강좌 순서를 적용한다. 정원·학점·시간 충돌로 취소를 거절하지 않는다. 취소와 재신청이 겹치면 학생 잠금을 획득한 순서대로 처리한다. 취소가 먼저 완료되면 재신청이 가능하고, 재신청 검사가 먼저 진행되어 기존 신청을 발견하면 중복 오류가 날 수 있다. 동시에 도착한 두 요청 모두 성공한다고 보장하지 않는다.

## 보장에 필요한 전제

- 신청·취소 등 신청 내역을 변경하는 모든 경로가 같은 잠금 규칙을 따른다. 부모 행 잠금만으로 임의의 자식 행 INSERT가 자동 차단되는 것은 아니다.
- 한 요청은 학생 한 명과 강좌 한 개를 처리한다. 여러 강좌를 한 번에 처리하는 기능은 추가 잠금 순서 설계가 필요하다.
- 신청 처리 중 과목 코드·학점·수업 시간·학기·정원 변경은 지원하지 않는다(D69). 운영 중 변경을 지원하려면 해당 변경 경로도 함께 보호하고 재검증해야 한다.
- 잠금 순서를 통일해 교착 위험을 줄이되 외래 키·다른 변경 경로까지 검토한다. 교착이 절대 발생하지 않는다고 가정하지 않는다.
- 타임아웃·교착 오류는 트랜잭션을 롤백한다. 이를 정원 초과 등 비즈니스 오류로 오인하지 않는다. 대기 한도와 응답은 D68 및 아래 정책을 따른다.

## 잠금 대기 실패 정책

신청·취소 모두 잠금 획득 시도별 대기 한도를 3초로 시작한다. 이는 초기 설정이며 측정된 적정값이 아니다. 요청 전체 제한 시간과는 다르며 실제 설정 방식은 구현 단계에서 결정하고 부하 테스트 후 조정한다.

잠금 대기 시간 초과 또는 교착 오류가 발생하면 전체 트랜잭션을 롤백한 뒤 HTTP 503 Service Unavailable로 응답한다.

~~~json
{
  "code": "ENROLLMENT_TEMPORARILY_UNAVAILABLE",
  "message": "일시적으로 요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요."
}
~~~

서버 자동 재시도는 현재 적용하지 않는다. 후속 검토 항목으로 재시도 대상 오류, 전체 트랜잭션 재실행, 최대 횟수·간격·총 대기 한도와 부하 영향을 남긴다. 정원 초과·중복 신청 등의 비즈니스 오류와 구분한다.

## 신청 순서와 데이터 모델

제안하는 ENROLLMENT 구조는 다음과 같다.

| 필드·제약 | 용도 |
|---|---|
| enrollment_id BIGINT IDENTITY PK | 생성 시 증가하는 신청 식별자이자 정렬 키 |
| student_number FK | 학생 |
| offering_id FK | 개설 강좌 |
| UNIQUE(student_number, offering_id) | 동일 강좌 중복 방지 |
| offering_id 인덱스 | 정원 검사와 강좌별 인원 집계 지원 |

내 시간표는 대상 학생·학기로 필터한 뒤 enrollment_id 오름차순으로 정렬한다. 이 값은 API 응답에 새로 노출할 필요가 없다.

증가 번호는 학생 잠금을 획득하고 모든 조건을 통과한 뒤 INSERT 시점에 발급한다. 같은 학생의 다음 신청은 이전 트랜잭션 종료 후 진행되므로 해당 학생의 성공한 저장 순서를 재현할 수 있다. 취소 후 재신청은 새 번호를 받는다.

DB 시퀀스는 롤백 시 값이 되돌아가지 않아 번호가 건너뛸 수 있다. 연속 번호를 요구하지 않는다. 서로 다른 학생 전체의 커밋 순서나 HTTP 도착 순서를 나타내는 값으로 사용하지 않는다. 같은 학생의 동시 요청도 먼저 클릭한 순서가 아니라 학생 잠금을 획득해 성공적으로 저장·커밋한 순서로 정의한다.

신청 시각만 사용하는 대안은 동률·정밀도·시각 생성 기준을 추가로 정해야 한다. 별도 시각 필드는 기록 목적이 생기면 검토하며, 현재는 증가 ID를 순서 키로 사용한다.

## 대안 비교

| 대안 | 검토 |
|---|---|
| 학생 행 낙관적 잠금 | 버전 변경을 강제하고 충돌 시 전체 작업을 재검증·재시도해야 함 |
| SERIALIZABLE | 직렬 실행과 동등한 결과를 보장하지만 충돌 시 전체 트랜잭션 재시도 설계가 필요 |
| 별도 정원 카운터 | 조건부 갱신으로 정원 제어 가능하나 신청·취소·초기 데이터와 카운터 일치 관리 필요 |
| 학생·강좌 행 비관적 잠금 + COUNT | 보호 대상을 설명하기 쉽고 현재 확정된 검사 순서에 맞음. 인기 강좌 대기와 COUNT 비용은 측정 필요 |

## 검증 계획

- JPA 실제 생성 SQL 및 목표 잠금 모드 확인(T108). 같은 잠금끼리 대기하며 KEY SHARE와 공존하는지 검증하고 필요 시 native query 전환 후 재검증.

- 학생·강좌 잠금 대기 한도 초과 및 교착 오류: 전체 롤백, 503 오류 본문, 자동 재시도 부재, 이후 잠금 해제 확인(T102~T103).

- 마지막 한 자리에 서로 다른 학생들이 동시 신청: 정확히 하나 성공, 최종 인원은 정원 이하.
- 15학점 학생이 서로 다른 3학점 강좌 두 개를 동시 신청: 정확히 하나 성공, 최종 18학점.
- 같은 학생의 시간 충돌 강좌·동일 과목 다른 분반·동일 강좌 동시 신청: 각각 정확히 하나 성공. 각 사례에서 다른 실패 조건은 제외.
- 학생 조건 실패: 강좌 잠금 획득 전 거절되는지 확인.
- 잠금 대기 후 최신 조회: 앞선 커밋의 신청 내역·인원이 다음 검사에 반영되는지 확인.
- 신청·취소·반복 취소 경합: 결과가 실제 직렬 처리 순서에 부합하고 타인 신청·다른 강좌가 삭제되지 않는지 확인.
- 강좌 잠금 뒤 예외: 신청 저장이 롤백되고 이후 요청이 잠금을 획득할 수 있는지 확인.
- A → B → C 순차 신청 후 A 취소·재신청: B → C → A. 롤백으로 신청 ID에 공백이 있어도 정렬 유지.
- 응답 개수와 커밋 후 DB 상태를 함께 검증한다. 성능 비교는 동일 조건의 실행 결과가 있을 때만 기록한다.

## 공식 근거

- [PostgreSQL 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS): 행 잠금 유지 구간과 FOR NO KEY UPDATE·KEY SHARE의 호환 관계.
- [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED): SQL 문마다 새 스냅샷을 사용하므로 잠금 이후 별도 조회로 앞선 커밋을 반영.
- [PostgreSQL 시퀀스](https://www.postgresql.org/docs/current/functions-sequence.html): nextval의 동시 호출과 롤백 시 번호 공백.
