# API 및 상세 설계 PR 초안

상태: PR 본문 초안. 구현·실행 결과 보고서가 아니다.

제안 제목: `docs: API 계약과 수강신청 동시성 정책 정의`

## 해결할 문제

초기 논리 설계만으로는 API 입력·오류 처리와 동시 요청의 처리 순서를 판단하기 어렵다. 확정 정책을 요청·응답 계약 및 검증 시나리오로 구체화하여 구현과 리뷰의 기준을 마련한다.

## 변경 및 근거

- 조회: [강좌](../API.md), [학생](../STUDENTS_API.md), [교수](../PROFESSORS_API.md)의 필터·페이지·정렬·응답·오류 계약.
- 인증 및 본인 작업: [로그인](../AUTH_API.md), [신청](../ENROLLMENTS_API.md), [취소](../CANCELLATIONS_API.md), [시간표](../TIMETABLE_API.md)의 계약.
- [요구사항](../REQUIREMENTS.md)과 [데이터 모델](../DATA_MODEL.md)에 학기·식별자·관계·입력 범위 및 검증 시나리오 반영.
- [동시성 설계](../CONCURRENCY_DESIGN.md)에 학생→강좌 잠금, READ COMMITTED, 잠금 후 조회·COUNT, 취소·실패 처리 및 SQL 검증 방침 정리.
- [기술 선택](../TECH_STACK_PROPOSAL.md), [변경·검증 계획](../DELIVERY_PLAN.md), [관련 설계 결정 정리](../../prompts/0002-api-design.md), README 탐색 경로 및 협업 규칙 반영.

확정 정책과 세부 구현 제안을 구분한다. 서버·DB 실행 설정 및 엔티티·업무 로직 구현은 후속 PR 범위이다.

## 검증 및 리뷰 기준

설계 브랜치에서 문서 22개, 상대 링크 대상 , JSON 예제  검사했다. 정책 D01~D78과 테스트 계획 T01~T112의 번호 누락·중복이 없다. 아래 항목을 AI 자체 리뷰에서 대조했다. 업무 API·DB 테스트는 실행하지 않았다.

- 요구사항과 7개 API의 인증·입력·학기·정렬·응답 계약이 일치하는가?
- 동일 강좌와 동일 과목 중복, 18학점, 맞닿은 수업 시간, 취소·재신청이 구분되는가?
- 학생과 강좌의 잠금 순서 및 실패 시 롤백이 신청·취소에 일관되게 적용되는가?
- SQL 잠금 모드와 성능을 검증 전 사실로 단정하지 않는가?
- 초기 데이터·건강 상태·인증을 포함한 구현 및 테스트 계획이 빠지지 않았는가?
- 문서 링크가 PR 브랜치에서 해석되며 미정 항목이 확정 사항으로 바뀌지 않았는가?

## AI 활용 및 리뷰

작성자가 정책과 관계를 결정하고 AI가 문서 정리와 검토를 지원했다. 관련 설계 결정을 주제별 제목과 본문으로 정리했다. [AI 자체 리뷰와 반영 결과](api-design-ai-review.md)를 기록했다. 사람 리뷰는 아직 수행되지 않았다. 기존 초기 설계 리뷰를 이번 변경 전체의 승인으로 간주하지 않는다.
