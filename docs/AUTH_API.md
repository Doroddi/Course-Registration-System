# 로그인 API

상태: 명세 초안 / 서버 미구현

[요구사항 D43~D53](REQUIREMENTS.md)에 따른 계약이다. 초기 학생 계정은 임의의 비밀번호가 설정된 상태로 생성하며, 현재 검증 범위는 학번·비밀번호 로그인부터이다. 이메일 임시 비밀번호와 최초 설정 흐름은 운영 설계로 구분한다.

## 요청

```http
POST /auth/login
Content-Type: application/json
```

```json
{
  "studentNumber": 202600001,
  "password": "example-password"
}
```

| 필드 | 필수 | 타입·의미 |
|---|---|---|
| studentNumber | 예 | JSON 숫자. 고정 9자리 학번(연도 4자리 + 뒤 5자리) |
| password | 예 | 문자열. 해당 학생의 비밀번호 |

예시 비밀번호는 요청 구조 설명용이며 초기 계정의 공통 비밀번호나 생성 규칙을 의미하지 않는다.

## 로그인 입력 검증

- studentNumber는 9자리 정수인 JSON 숫자여야 한다. 숫자 문자열을 대신 받지 않는다.
- password는 문자열이며 빈 문자열·공백만 있는 값은 거절한다. 앞뒤 공백을 제거하지 않고 입력 그대로 인증한다.
- 필드 누락·null·타입 불일치·잘못된 JSON은 400 INVALID_PARAMETER이다.
- 파싱 가능한 요청의 필드 검사는 studentNumber → password 순서로 수행하고, 통과한 뒤 계정을 인증한다. 역직렬화 오류와 필드 오류가 함께 있을 때의 우선순위는 후속 설계한다.

## 토큰 응답과 사용

인증 성공 시 HTTP 200과 accessToken·tokenType·expiresIn을 반환한다. expiresIn은 발급 시점 기준 유효기간을 초 단위 숫자로 나타낸다. 아래 JWT 문자열은 실제 토큰이 아닌 자리표시자이다.

```json
{
  "accessToken": "<JWT>",
  "tokenType": "Bearer",
  "expiresIn": 1800
}
```

요청과 응답의 영문 필드명은 기존 camelCase 규칙을 따른다. 이후 수강신청 요청에는 다음 헤더를 사용한다.

```http
Authorization: Bearer <accessToken>
```

JWT는 토큰 형식, Bearer는 전달·사용 방식이다. 서버는 검증된 토큰의 학번으로 신청자를 식별한다. 클레임과 유효기간은 아래를 따른다. 서명 방식과 검증 세부 조건은 후속 설계한다.

## JWT 클레임과 유효기간

| 클레임 | 의미 | 표현 |
|---|---|---|
| sub | 학생 학번 | 문자열. 예: "202600001" |
| iss | 발급자 | 구체적 식별값은 미정 |
| aud | 토큰 사용 대상 | 구체적 식별값은 미정 |
| iat | 발급 시각 | Unix 시간의 초 단위 숫자 |
| exp | 만료 시각 | iat + 1800초 |

sub는 JWT 표준의 문자열 표현을 사용하며 로그인 요청과 DB의 학번 숫자 타입은 유지한다.

- 유효기간은 발급 후 30분이다. 만료 시각부터 토큰을 사용할 수 없으며 재로그인해야 한다.
- 만료 전에는 재발급 요청을 할 수 있다. 재발급 경로·인증 조건·횟수·기존 토큰 처리·새 토큰 만료 산정은 아직 확정하지 않았다.
- 재발급 요청이 가능하다는 정책만으로 별도의 refresh token 도입을 확정하지 않는다.

## 시간 기준과 인증 적용 범위

날짜·시각의 해석과 표시는 KST(Asia/Seoul, UTC+09:00)를 따른다. JWT iat·exp는 시간대와 무관하게 같은 순간을 나타내는 Unix 시간의 초 단위 숫자이다. 숫자에 9시간을 더하지 않으며, exp - iat = 1800초를 유지한다. 이는 [JWT NumericDate 정의](https://www.rfc-editor.org/rfc/rfc7519.html#section-2)에 따른다.

- 강좌·학생·교수 목록 조회는 로그인 후에만 허용한다.
- 수강신청·취소·시간표 조회는 검증된 JWT의 sub로 학생을 식별한다. 별도 요청 학번으로 대상을 변경할 수 없다.
- 인증이 필요한 API의 토큰 누락·위조·만료는 모두 401이다. 오류 code·message는 미정이다.
- 강좌 목록도 Authorization: Bearer <accessToken>으로 유효한 JWT를 전달해야 한다. 세부 인가 정책은 후속 결정한다.

## 확정된 오류 상태

| 상황 | HTTP 상태 |
|---|---|
| 필수 필드 누락·null·타입 불일치·형식 오류·잘못된 JSON | 400 Bad Request |
| 존재하지 않는 학번 또는 비밀번호 불일치 | 401 Unauthorized |

로그인 실패 시 토큰을 발급하지 않는다. 입력 오류는 INVALID_PARAMETER, 인증 불일치는 INVALID_CREDENTIALS를 사용한다. 인증 불일치 메시지는 "학번 또는 비밀번호가 올바르지 않습니다."로 통일한다. 입력 오류의 구체적 message는 미정이다.

## 후속 결정

- 입력 오류 message, JSON 중복·지원하지 않는 필드 처리, 역직렬화 오류와 필드 검증의 우선순위
- 비밀번호 저장·검증 방식과 초기 계정 비밀번호의 생성·테스트용 전달 방식
- JWT 서명 알고리즘·키 관리, iss·aud의 구체적 값과 검증 세부 조건
- 만료 전 재발급 API·인증 조건·횟수·기존 토큰 처리 등 세부 정책, 로그아웃 정책, 세부 인가 정책 및 토큰 오류 본문
- 배포 환경의 HTTPS 구성

검증 시나리오: 요구사항 T58~T74. 서버 테스트는 아직 실행하지 않았다.
