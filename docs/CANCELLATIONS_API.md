# 수강취소 API

상태: DELETE /enrollments/{courseOfferingId} 구현 / 검증 결과는 아래 기록 참조

기존 확정 정책은 요구사항 D09~D11, D50~D51, D61~D62를 따른다. 대상 학기 제한, 취소 잠금 순서(D67), 잠금 실패 처리(D68)를 반영했다. 경로·성공 응답·없는 강좌 처리는 D70으로 확정했다.

## 기존 확정 정책

- 로그인한 학생은 검증된 JWT의 sub로 식별한다.
- 취소는 현재 신청 내역을 삭제하며 취소 이력은 보관하지 않는다.
- 학생·강좌가 존재할 때 신청 내역이 없거나 이미 취소되었어도 성공한다.
- 토큰 누락·위조·만료는 401이다. 토큰 발급 후 학생 삭제는 범위에서 제외한다.

## 요청·응답

```http
DELETE /enrollments/11
Authorization: Bearer <accessToken>
```

경로 변수는 courseOfferingId이다. 학생 학번과 요청 본문은 받지 않는다. sub의 학생과 경로의 개설 강좌에 해당하는 신청 관계만 삭제한다.

성공은 HTTP 204 No Content이며 응답 본문이 없다. 신청 내역이 원래 없거나 이미 취소된 경우도 같은 응답을 사용한다. 존재하지 않는 강좌는 신청 내역이 없는 경우와 구분한다.

## 오류 계약

기존 수강신청의 입력·오류 표기 규칙을 재사용한다.

| 상황 | HTTP 상태 | code | message |
|---|---|---|---|
| 개설 강좌 ID가 양의 정수 형식이 아님 | 400 | INVALID_PARAMETER | 잘못된 요청입니다. |
| 토큰 누락·위조·만료 | 401 | TOKEN_REQUIRED / TOKEN_EXPIRED / INVALID_TOKEN | [인증 명세](AUTH_API.md)의 원인별 메시지 |
| 개설 강좌가 존재하지 않음 | 404 | COURSE_OFFERING_NOT_FOUND | 존재하지 않는 강좌입니다. |
| 취소 대상 학기가 아님 | 409 | INVALID_ENROLLMENT_TERM | 신청 대상 학기가 아닙니다. |

대상 학기 외 취소의 409 응답은 D62에 따른다. ID 물리 타입은 BIGINT·Java Long(D76)이며 입력 범위는 1~Long.MAX_VALUE이다. ASCII 숫자 0~9로 구성된 경로를 받고 선행 0은 허용한다. 공백·부호·소수·지수 표기는 거절한다.

## 대상 학기와 처리 순서

취소도 서버에 설정된 신청 대상 연도·학기로 제한한다. 신청과 취소가 같은 학기를 대상으로 동작하게 하고, 다른 학기의 신청 내역 변경을 방지하려는 목적이다.

처리 순서: 인증 → 경로 입력 검증 → 개설 강좌 존재 확인 → 대상 학기 확인 → 학생 행 잠금 → 개설 강좌 행 잠금 → 본인 신청 내역 삭제 → 커밋 → 204. 잠금 순서는 D67, 경로·성공 응답은 D70을 따른다.

정원·18학점·시간표 충돌은 새 신청을 제한하는 조건이므로 취소를 거절하는 조건으로 사용하지 않는다. 신청과 같은 학생 → 강좌 순서의 잠금을 트랜잭션 종료까지 유지한다. 잠금 적용 방침은 D75를 따르며 신청과 동일한 Repository 잠금 메서드를 사용한다. 현재 인원은 신청 테이블 COUNT로 계산하며 별도 카운터는 갱신하지 않는다.

## 검증 계획

- 신청 내역이 있는 경우 삭제 후 204, 같은 취소를 반복해도 204.
- 다른 학생만 해당 강좌를 신청한 경우 타인의 신청은 유지하고 204.
- 같은 과목의 다른 분반 신청은 삭제하지 않음.
- 존재하지 않는 강좌는 404. 대상 학기 외 강좌는 409이며 기존 신청 내역 유지(T95).
- 인증·입력 오류 시 삭제 미수행.
- 신청·취소 경합 및 인원 집계 정합성은 T101, 잠금 대기 실패·교착 롤백은 T102~T103으로 검증한다.

위 목록은 검증 계획이며 실제 실행 결과는 아래에 구분한다.

## 확정된 잠금 실패 응답

D68에 따라 잠금 획득 시도별 3초 대기 한도로 시작한다. 시간 초과 또는 교착 오류 시 전체 롤백 후 503 ENROLLMENT_TEMPORARILY_UNAVAILABLE과 메시지 일시적으로 요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.를 반환한다. 서버 자동 재시도는 현재 적용하지 않으며 후속 검토한다. 트랜잭션 한정 set_config로 lock_timeout=3s를 적용하며 대기 한도는 부하 테스트 후 조정한다.

## 구현 의도

취소는 신청과 같은 EnrollmentController·EnrollmentService를 사용하고 같은 잠금 실패 처리기를 거친다. 학생·강좌 잠금을 획득한 후 JPQL bulk DELETE로 JWT sub의 학생과 경로 ID가 일치하는 신청만 삭제한다. 신청 존재 확인을 위한 SELECT는 실행하지 않으며 삭제 0건도 204이다.

현재 취소 트랜잭션에서는 Enrollment 엔티티를 로드하지 않으므로 bulk DELETE 이후 영속성 컨텍스트를 초기화하지 않는다. 신청 이력·수강 인원 카운터·학점 카운터는 추가하지 않는다. 실제 삭제가 커밋된 뒤에만 204를 반환하며 DB 오류 시 기존 신청은 롤백으로 복구된다.

공식 근거: [Spring Data JPA 수정·삭제 쿼리](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html#jpa.modifying-queries). 2026-09-25 Spring Data JPA 4.1.1 문서에서 @Modifying과 bulk 쿼리의 영속성 컨텍스트 주의 사항을 확인했다.
## 실제 검증 결과

2026-09-25: 신청·취소 관련 80개 테스트가 통과했다(HTTP·PostgreSQL 통합 74개, 오류 분류 단위 6개). 이번 취소 구현에서 통합 사례 27개를 추가했으며 실패·오류·건너뜀 0, bootJar 성공이다. Testcontainers PostgreSQL 18.6에서 실행했고 실행 JAR에 테스트 코드가 포함되지 않은 것을 확인했다.

~~~text
./gradlew test --tests '*EnrollmentIntegrationTest' --tests '*EnrollmentExceptionHandlerTest' bootJar --no-daemon
~~~

- 본인·대상 강좌 신청만 삭제, 타인·다른 분반 신청 보존, 반복 취소와 미신청 취소의 본문 없는 204.
- 경로 형식·범위 및 인증 오류 시 DB 접근 없음, 없는 강좌 404, 대상 학기 외 409와 신청 보존.
- 실제 SQL에서 학생 → 강좌 FOR NO KEY UPDATE → DELETE 순서와 READ COMMITTED 확인.
- 취소 후 재신청 시 새 신청 ID 발급 및 다른 강좌와의 신청 순서 유지.
- 동시에 반복 취소해도 모두 204이며 타인 신청 보존.
- 동일 학생의 신청 → 취소, 취소 → 신청을 각각 선행 잠금과 커밋으로 통제해 최종 상태 확인.
- 취소 커밋으로 생긴 마지막 자리를 기다리던 다른 학생의 신청이 사용하며 정원 이하 유지.
- 학생·강좌 잠금 대기 초과, 실제 교착, DELETE 실패 시 기존 신청 보존 및 후속 취소 성공.

전체 541개 테스트 통과 기록은 선행 신청 구현 시점의 결과이다. 취소 변경 후에는 위 80개를 실행했으며 전체 프로젝트를 다시 실행한 결과로 해석하지 않는다. 시간표 API와 대규모 부하 성능 검증은 남아 있다.
