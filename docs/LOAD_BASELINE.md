# HTTP 부하 기준값

## 목적과 측정 방법

성능 합격선을 먼저 정하지 않고 현재 구현의 기준값을 측정한다. 학생 → 강좌 잠금 순서, READ COMMITTED, 잠금 대기 3초, 자동 재시도 없음 정책과 운영 코드·연결 풀 설정을 유지한다.

`scripts/verify-initial-data.ps1`이 별도 PostgreSQL 컨테이너와 실행 JAR를 준비하고 `scripts/measure-load-baseline.ps1`이 로그인·부하 실행·종료 검증을 담당한다. 개발 DB에 연결하지 않는다. `scripts/load-baseline.js`는 k6에서 HTTP 요청과 결과 분류를 수행한다. 테스트용 토큰 파일은 실행 후 삭제하며 결과에는 토큰·비밀번호를 기록하지 않는다.

~~~powershell
./scripts/verify-initial-data.ps1 -FirstOnly -ApiSmoke -LoadBaseline
~~~

조건별 준비 운전 10초, 본 측정 30초를 각각 별도 k6 실행으로 수행한다. 각 실행 전 임시 DB의 신청만 초기화한다. 로그인은 측정 밖에서 수행하며 사용자마다 서로 다른 학생 계정을 사용한다. 집중 → 분산 → 혼합 순서로 각각 10·50·100명을 실행한다. 순서에 따른 JVM 워밍업 효과를 통제한 반복 실험은 아니다.

| 조건 | 부하 구성 |
|---|---|
| 집중 | 모든 사용자가 정원 30명인 동일 강좌에 신청하고 성공 후 취소 |
| 분산 | 사용자마다 다른 강좌에 신청하고 성공 후 취소 |
| 혼합 | 사용자 20%는 동일 강좌 신청·취소, 나머지 80%는 강좌 첫 페이지(size=20)·본인 시간표 순차 조회 |

혼합 비율은 **사용자 수** 기준이다. API별 속도 차이로 요청 건수 비율은 달라진다. 읽기 사용자에게 초기 신청은 없으므로 시간표는 빈 목록이다. 신청 성공을 취소로 되돌려 정원이 찬 뒤 빠른 거절만 측정하는 상황을 줄인다. 각 사용자는 동시에 한 요청만 보내며 별도 생각 시간은 없다. 실패 요청을 재시도하지 않으며 409 외 오류는 커밋 여부가 불명확할 수 있어 취소로 정리한다.

## 지표의 의미

- 성공(신청 201·취소 204·조회 200), 업무 거절(신청 409), 일시 실패(503), 그 외 응답/전송 오류를 분리한다. 409는 오류 코드별로도 센다. 예상 밖 응답은 실행 실패로 처리한다.
- 처리량은 실제 실행 시간(종료 중 진행 요청을 마치는 시간 포함)으로 나눈 완료 요청 수다. k6 `constant-vus`는 응답이 느려지면 다음 요청도 늦어지는 폐쇄형 모델이다. 고정된 유입률을 견뎠거나 최대 처리량을 찾았다는 뜻이 아니다.
- 지연 시간은 k6 HTTP 요청의 전송·대기·수신 시간(ms)이다. DNS·초기 연결·연결 슬롯 대기는 포함하지 않는다. 작업별·결과별 p95/p99를 분리한다. 표본이 없으면 백분위도 없다.
- 각 실행은 최대 35초 동안 진행 중인 반복을 마칠 수 있다. HTTP 요청 제한은 30초다. 이는 테스트 도구 설정이며 서비스 정책이 아니다. DB 잠금 대기 3초는 요청 전체의 응답 제한 시간이 아니다.
- 본 측정 종료 후 정원·18학점·동일 과목·시간 충돌 위반 및 남은 신청을 SQL로 확인한다. 신청·취소 순환 후의 최종 상태 확인이므로 모든 중간 시점의 불변식을 증명하지 않는다. 별도 동시성 통합 테스트와 구분한다.
- 정확한 DB 잠금 대기 시간, Hikari 대기자 수, CPU/메모리 시계열은 이번 지표에 없다. HTTP 지연만으로 병목 원인을 단정하지 않는다.

## 도구와 재현 근거

k6 2.3.0 컨테이너 이미지를 digest까지 고정했다. 서버와 DB, 부하 생성기가 같은 장비 자원을 공유하는 로컬 측정이며 전용 부하 장비 결과가 아니다. JAR 해시·Docker 자원 한도·OS·실행 조건은 `load-environment.json`, 조건별 원본 집계는 개별 JSON 및 `load-results.json`에 저장한다. 출력 위치는 실행 마지막의 `LOAD_RESULTS`에 표시한다.

사용한 공식 문서: [폐쇄형·개방형 부하 모델](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/), [HTTP 지표](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/), [사용자 정의 지표](https://grafana.com/docs/k6/latest/using-k6/metrics/create-custom-metrics/), [종료 집계 저장](https://grafana.com/docs/k6/latest/results-output/end-of-test/custom-summary/).

### 해석과 후속 범위

집중 부하 100명의 전체 처리량에는 1,270건의 정원 초과 거절이 포함된다. 전체 req/s가 높아도 성공 신청 처리량이 늘었다고 해석할 수 없다. 분산 부하에서도 100명에서는 50명보다 성공 신청 처리량이 감소하고 지연이 증가했다. 같은 강좌의 잠금 경쟁 외에도 공유 자원·연결 풀·DB·JVM·부하 생성기 상태를 계측해야 원인을 좁힐 수 있다.

이는 조건별 30초의 첫 탐색 결과다. 반복 편차·실험 순서 효과·다른 장비·실제 사용자 행동을 검증하지 않았다. 다음 단계는 병목 계측을 추가한 비교 반복이며, 그 근거를 바탕으로 성능 목표 또는 개선 여부를 결정한다. 이번 측정을 이유로 잠금·타임아웃·연결 풀 설정을 변경하지 않았다.

후속 [정원 경쟁·부하 진단](LOAD_DIAGNOSTICS.md)에서 200명 단발 신청과 연결 풀·잠금·쿼리·자원 계측 결과를 구분해 기록한다.
