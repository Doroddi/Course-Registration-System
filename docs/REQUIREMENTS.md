# 요구사항 및 설계 결정

상태: V1~V10·JPA, 초기 데이터 생성·검증, 대상 학기 설정과 /health, 로그인·JWT 인증 구현 / 갱신일: 2026-09-23. 최신 인증 구현과 검증은 [로그인·JWT 인증](AUTH_API.md)을 따른다. 목록의 공통 입력 검증·페이지 응답을 구현했으며 실제 검증 결과는 [공통 구현](LIST_QUERY_COMMON.md)을 따른다. 학생·교수 목록 API를 구현·검증했으며 실행 결과는 [목록 구현·검증](LIST_QUERY_COMMON.md#학생교수-목록-연결)을 따른다. 강좌 목록도 구현·검증했으며 [강좌 API](API.md#구현검증)에 실행 결과를 구분한다. 신청·취소·시간표와 신청 동시성은 후속 구현 대상. [초기 데이터 문서](INITIAL_DATA.md)와 [실제 측정 기록](INITIAL_DATA_PERFORMANCE.md)을 따른다.

원문: [무신사 대학교 수강신청 과제](https://github.com/musinsatech/2026-musinsa-rookie/blob/main/PROBLEM.md) (2026-09-12 확인). 원 과제의 요구, 추가 확정 정책, 검토 중인 제안을 구분한다. 관련 문서는 [ERD](DATA_MODEL.md)와 [설계 결정 정리](../prompts/0001-design-conversation.md)이다.

## 1. 목적과 기능 범위

학생·강좌·교수 조회와 수강신청·취소·시간표 조회를 REST API로 제공한다. 동시 요청에서도 정원, 학점, 시간 충돌 제약을 유지하는 것을 목표로 한다. 구현 범위는 백엔드 API이다.

| ID | 원 과제 기능 | 완료 판단 기준 |
|---|---|---|
| F01 | 학생 목록 | 유효한 학생 식별자를 조회할 수 있다. |
| F02 | 전체·학과별 강좌 목록 | 강좌 식별자, 이름, 학점, 정원, 신청 인원, 수업 시간을 확인할 수 있다. |
| F03 | 교수 목록 | 유효한 교수 식별자를 조회할 수 있다. |
| F04 | 수강신청 | 아래 불변식과 정책을 지키며 신청을 저장한다. |
| F05 | 수강취소 | 신청 관계를 제거한다. |
| F06 | 이번 학기 시간표 | 학생의 대상 학기 신청 강좌와 수업 시간을 반환한다. |
| F07 | GET /health | 데이터 준비 및 API 사용 가능 상태에서 HTTP 200을 반환한다. |

## 2. 불변식

| ID | 항상 유지해야 하는 조건 | 출처 |
|---|---|---|
| I01 | 개설 강좌의 신청 수는 정원을 초과하지 않는다. | 원 과제 |
| I02 | 학생의 같은 연도·학기 신청 학점 합은 18 이하이다. | 원 과제 |
| I03 | 학생의 같은 연도·학기 신청 강좌 수업 시간이 서로 겹치지 않는다. | 원 과제 |
| I04 | 같은 학생은 같은 개설 강좌에 중복 신청할 수 없다. | 추가 정책 |
| I05 | 같은 학생은 같은 연도·학기에 같은 과목의 여러 분반을 신청할 수 없다. | 추가 정책 |

이 조건들은 순차 요청뿐 아니라 동시 요청에도 유지되어야 한다. 검사와 저장을 각각 수행하는 것만으로는 보장되지 않는다. 학생·강좌 행 잠금과 READ COMMITTED는 D64~D65를 따른다. 취소 잠금 흐름과 실패 처리는 D67~D68을 따른다. 잠금 적용 방침은 D75를 따르며 실제 생성 SQL과 동작은 구현 시 검증한다.

## 3. 확정 정책

| ID | 정책 | 근거·영향 |
|---|---|---|
| D01 | 학번은 유일하고 변경되지 않으며 학생 PK로 사용한다. | 학번의 유일성과 불변성을 도메인 전제로 둔다. |
| D02 | 학생은 학번 외에 이름·소속 학과·학년을 저장한다. 전화번호·생년월일은 제외한다. | 필요한 프로필만 유지한다. 학생 학과는 학생 소속을 나타내며, 학과별 강좌 조회는 강좌 학과를 사용한다. |
| D03 | 과목 코드로 과목을 구별한다. 개설 강좌는 특정 연도·학기의 분반이다. | 동일 과목의 다른 분반 중복을 판별한다. |
| D04 | 개설 강좌에 별도 PK를 두며, 강좌코드는 같은 연도·학기 안에서 유일하다. | 다음 학기에 강좌코드를 재사용할 수 있다. |
| D05 | 학기 테이블 없이 개설 강좌에 연도와 학기를 저장한다. | 현재는 학기 자체의 독립적인 관리 요구가 없다. |
| D06 | 서버 설정의 대상 연도·학기에 대해서만 신청한다. 이번 학기 시간표도 이 대상을 사용한다. | 날짜와 독립적으로 다음 학기 신청을 운영할 수 있다. 학점·과목 중복·시간 충돌 검사도 대상 학기 기준이다. |
| D07 | 이미 신청한 개설 강좌의 신청은 거절하고 이미 신청했다는 이유를 전달한다. | 요청 중복으로 신청·학점이 늘어나지 않는다. |
| D08 | 수업 종료 시각과 다음 수업 시작 시각이 같으면 함께 신청할 수 있다. | 시간 구간의 경계가 맞닿는 연속 수업을 허용한다. |
| D09 | 취소한 강좌에 재신청할 수 있다. | 재신청 당시 모든 조건을 다시 검사하며 자리를 예약해 두지 않는다. |
| D10 | 신청 대상 학기의 강좌가 존재할 때 신청 내역이 없거나 이미 취소돼도 취소는 성공한다. | 클라이언트가 신청 상태를 먼저 구분할 필요가 없다. 토큰 발급 후 학생 삭제는 D61에 따라 범위에서 제외한다. 취소 대상 강좌가 존재하지 않으면 D70에 따라 404를 반환한다. |
| D11 | 현재 신청만 저장하고 취소하면 수강신청 행을 삭제한다. 상태 컬럼과 취소 이력 정리 작업은 두지 않는다. | 취소 이력 보관 요구가 없어 현재 관계만 관리한다. 재신청은 새 관계 행을 추가한다. |
| D12 | 수업 시간은 별도 테이블에 요일·시작·종료 시각을 저장하고 개설 강좌와 1:N으로 연결한다. | 한 강좌의 복수 수업 시간을 표현한다. |
| D13 | 학과·교수를 별도 테이블로 둔다. 교수는 하나의 학과에 소속된다. | 소속 정보와 담당 관계를 구분한다. |
| D14 | 개설 강좌에 소속 학과를 연결하며 타 학과 교수도 담당할 수 있다. | 교수 소속과 강좌 개설 학과는 다른 사실이다. |
| D15 | 교수와 개설 강좌는 N:M이며 공동 강의를 허용한다. | 강의 담당 연결 테이블로 여러 교수를 표현한다. 원 과제에 추가한 정책이다. |
| D16 | 전체·학과별 강좌 목록은 서버 설정의 신청 대상 연도·학기만 조회한다. | 조회 범위와 신청 가능 학기를 일치시킨다. 클라이언트가 다른 학기를 선택하는 조회 기능은 제공하지 않는다. |
| D17 | 전체·학과별 강좌 목록은 페이지 번호 방식으로 제공한다. | 강좌 목록의 조회 방식과 예상 규모를 고려해 선택했다. 성능 검증은 후속 작업이다. |
| D18 | 전체·학과별 강좌 목록은 강좌 코드(offeringCode) 오름차순으로 정렬한다. | 기존 강좌명·개설 강좌 ID 정렬을 변경한다. 강좌 코드는 대상 학기 내에서 유일하다. 숫자로 구성된 문자열을 숫자 크기순으로 비교한다. 선행 0은 저장 시 보존하며 숫자값이 같은 코드는 개설 강좌 ID 오름차순으로 구분한다. 최대 30자리 값을 정확히 비교한다. |
| D19 | 강좌 목록의 첫 페이지 번호는 0이며, 페이지 크기의 기본값은 20, 최댓값은 100이다. | 일정한 기본 응답 크기와 요청당 상한을 둔다. 크기는 초기 정책이며 성능 측정으로 도출한 값은 아니다. |
| D20 | 페이지 번호·크기를 생략하면 각각 0·20을 적용한다. 음수 페이지, 크기 1~100 밖의 값, 숫자가 아닌 값은 오류로 응답한다. 유효한 페이지 번호에 조회 결과가 없으면 성공과 빈 목록을 반환한다. | 잘못된 요청을 자동 보정하지 않고 알리며, 조회 결과 부재와 입력 오류를 구분한다. HTTP 상태 코드는 D26을 따른다. 숫자 형식·상한과 offset 범위는 D90을 따른다. |
| D21 | 강좌 목록 응답은 목록(content), 현재 페이지(page), 페이지 크기(size), 전체 건수(totalElements), 전체 페이지 수(totalPages)를 포함한다. | 전체 건수는 대상 학기와 선택한 학과 조건에 맞는 개설 강좌 수이다. 전체 페이지 수는 전체 건수를 페이지 크기로 나눈 값을 올림하여 계산한다. |
| D22 | 강좌 목록의 각 항목은 개설 강좌 ID·강좌명·학점·정원·현재 신청 인원과 수업 시간 배열을 제공한다. 소속 학과는 departmentName 문자열, 담당 교수는 ID·이름 객체 배열로 제공한다. | 수업 시간은 요일·시작·종료 시각을 포함한다. 학과는 표시용 이름만 제공하고, 교수는 이름이 같아도 ID로 구분하며 공동 강의를 표현한다. JSON 필드명은 D23, 요일·시각 형식은 D24를 따른다. |
| D23 | 강좌 항목은 id, name, credits, capacity, enrolled, schedules, departmentName, professors 필드를 사용한다. 수업 시간은 dayOfWeek, startTime, endTime, 교수 객체는 id, name을 사용한다. | 영문 camelCase로 페이지 응답 필드와 표기 방식을 통일한다. |
| D24 | dayOfWeek는 MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY 중 하나를 사용한다. startTime과 endTime은 24시간제 HH:mm 문자열로 표현한다. | 요일 표기를 통일하고 시각을 시·분 각각 두 자리로 제공한다. 수업 범위는 D77에 따라 같은 날 시작·종료한다. |
| D25 | 학과 필터의 ID가 존재하지 않으면 학과를 찾을 수 없다는 오류를 반환한다. 학과가 존재하지만 대상 학기 강좌가 없으면 성공 응답과 빈 목록을 반환한다. | 잘못된 학과 식별자와 조회 결과 부재를 구분한다. HTTP 상태 코드와 오류 본문은 D26을 따른다. |
| D26 | GET /course-offerings에서 departmentId, page, size 쿼리 파라미터를 사용한다. departmentId 생략 시 대상 학기 전체 강좌를 조회한다. 정상·빈 목록은 200, 잘못된 파라미터는 400, 존재하지 않는 학과는 404로 응답한다. 오류 본문은 code와 message이며 학과 부재 코드는 DEPARTMENT_NOT_FOUND이다. | 입력 오류·리소스 부재·정상 조회를 구분한다. 상세 계약은 [강좌 목록 API](API.md)에 정리한다. |
| D27 | 강좌 목록의 잘못된 파라미터는 HTTP 400, code=INVALID_PARAMETER로 응답한다. message는 잘못된 항목과 허용 범위 또는 형식을 설명한다. | 클라이언트가 고정 코드로 오류 종류를 구분하고 메시지로 수정할 입력을 확인할 수 있게 한다. |
| D28 | 강좌 목록은 파라미터 형식·범위를 먼저 검사하고, 유효한 경우에만 학과 존재 여부를 조회한다. 입력 오류와 학과 부재가 함께 해당되면 400 INVALID_PARAMETER를 우선 반환한다. | 유효하지 않은 요청에서 학과·강좌·건수 조회를 수행하지 않는다. 여러 입력 오류의 우선순위는 D29를 따른다. |
| D29 | 강좌 목록의 알려진 파라미터는 departmentId → page → size 순서로 각 항목의 중복 → 형식·범위를 검사하고 첫 오류 하나만 400 INVALID_PARAMETER로 반환한다. | 지원하지 않는 이름을 먼저 검사하는 전체 우선순위는 D91을 따른다. 쿼리 파라미터 나열 순서와 무관하게 동일한 오류를 선택한다. 학과 존재 여부는 offset을 포함한 모든 입력 검사가 통과한 뒤 확인한다. |
| D30 | departmentId는 양의 정수, page는 0 이상의 정수, size는 1~100의 정수로 제한한다. 소수·공백만 있는 값·빈 문자열은 400 INVALID_PARAMETER로 거절한다. | 기본값과 학과 필터 미적용은 파라미터 자체가 생략된 경우에만 적용한다. ASCII 숫자 형식·선행 0 허용·표현 상한과 offset 범위는 D90을 따른다. |
| D31 | 강좌 목록 요청에서 같은 파라미터를 여러 번 전달하거나 departmentId·page·size 외의 파라미터를 전달하면 400 INVALID_PARAMETER로 거절한다. | 중복 값 중 하나를 임의 선택하거나 알 수 없는 파라미터를 무시하지 않는다. message에 중복 항목 또는 지원하지 않는 이름을 설명한다. |
| D32 | 학생 목록에 페이지 번호 방식을 적용하고 content, page, size, totalElements, totalPages 구조로 응답한다. 첫 페이지와 기본 페이지는 0, 기본 크기는 20, 최대 크기는 100이다. | 강좌 목록과 페이지 응답 구조·기본값을 통일한다. 학생 목록의 경로·정렬·필터·항목 필드는 D35를 따른다. 학생 목록의 오류 정책은 D36을 따른다. |

### 상태 보관 결정의 변경

취소 상태를 저장하고 나중에 정리하는 방안과 취소 시 행을 삭제하는 방안을 비교했다. 취소 이력 보관 요구가 없으므로 상태 필터링·재활성화·정리 작업을 줄이는 D11을 선택했다. 성능 우위는 이 결정의 근거로 사용하지 않는다. 결정 과정은 [설계 결정 정리의 수강신청 관계와 취소 데이터](../prompts/0001-design-conversation.md#4-수강신청-관계와-취소-데이터)에 정리했다.

### 시간 충돌의 표현

같은 요일의 수업 A와 B가 `A.start < B.end` 그리고 `B.start < A.end`이면 충돌한다. 반열린 구간 `[시작, 종료)`로 D08을 표현한 것이다. 서로 다른 요일은 충돌하지 않는다. 수업은 D77에 따라 매주 반복하며 같은 날 시작·종료한다.

## 4. 초기 데이터 및 제출 요구

원 과제 기준으로 학과 10개, 개설 강좌 500개, 학생 10,000명, 교수 100명 이상을 실행 시 생성한다. 현실적인 이름·패턴을 사용하고, 완성 레코드가 담긴 정적 SQL·CSV나 대량 리터럴로 대체하지 않는다. 소규모 이름 토큰은 사용할 수 있다. 데이터 생성과 헬스체크 준비는 시작 후 1분 이내이며 생성 결과도 비즈니스 규칙을 지켜야 한다.

빌드·실행법, 에이전트 지침, 설계 결정 기록, 요구사항, 요청·응답·오류·예제를 포함한 API 문서가 필요하다. 7개 API 명세를 작성했으며 학생·교수·강좌 목록 API를 구현했다. 신청·취소·시간표 API는 후속 구현 대상이다. 요구 규모의 전체 초기 데이터 생성·검증과 기동 준비 상태를 구현했다. 실행 기반 검증은 별도 변경 단위에서 기록한다.

신청 기간·학년별 시간 제한은 미정이다. 공동 강의의 담당 요일·대표 교수·기여율도 후속 요구사항 검토 대상으로 둔다.

이메일 기반 최초 설정의 운영 설계(D46)는 현재 모의 처리와 구분한다. 이메일 주소의 확보·소유 확인·저장 위치와 임시 비밀번호의 유효기간·사용 제한은 미정이다. 학생 프로필에 이메일 필드를 추가할지는 아직 확정하지 않았다.

취소·시간표 API 계약: [수강취소 API](CANCELLATIONS_API.md)와 [내 시간표 API](TIMETABLE_API.md)에 D70~D72의 확정 경로·응답·정렬·조회 일관성을 반영한다. 실제 SQL 구성은 구현 단계에서 결정하며 인증 오류 본문은 공통 인증 설계에서 확정한다.

[신청·취소 동시성 설계](CONCURRENCY_DESIGN.md)에 D64~D69의 확정 사항과 잠금 모드·물리 타입 등 남은 제안을 구분한다.

자동 재시도는 현재 구현하지 않는다(D68). 후속 검토 시 재시도 대상 오류, 전체 트랜잭션 재실행, 최대 횟수·간격·총 대기 한도와 부하 영향을 함께 결정한다.

[기술 스택·물리 데이터 모델](TECH_STACK_PROPOSAL.md)에 D73~D74의 확정 기술 스택과 물리 설계 제안, JPA 구현 검토 순서를 구분한다.
