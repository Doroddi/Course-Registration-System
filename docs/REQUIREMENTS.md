# 요구사항 및 설계 결정

상태: 첫 설계 검토 초안 / 정리일: 2026-09-12 / 구현 및 검증: 미실시

원문: [무신사 대학교 수강신청 과제](https://github.com/musinsatech/2026-musinsa-rookie/blob/main/PROBLEM.md) (2026-09-12 확인). 원 과제의 요구, 추가 확정 정책, 검토 중인 제안을 구분한다. 관련 문서는 [ERD](DATA_MODEL.md)와 [설계 관련 프롬프트 발췌](../prompts/0001-design-conversation.md)이다.

## 1. 목적과 기능 범위

학생·강좌·교수 조회와 수강신청·취소·시간표 조회를 REST API로 제공한다. 동시 요청에서도 정원, 학점, 시간 충돌 제약을 유지하는 것을 목표로 한다. 구현 범위는 백엔드 API이다.

| ID | 원 과제 기능 | 완료 판단 기준 |
|---|---|---|
| F01 | 학생 목록 | 유효한 학생 식별자를 조회할 수 있다. |
| F02 | 전체·학과별 강좌 목록 | 강좌 식별자, 이름, 학점, 정원, 신청 인원, 수업 시간을 확인할 수 있다. |
| F03 | 교수 목록 | 유효한 교수 식별자를 조회할 수 있다. |
| F04 | 수강신청 | 아래 불변식과 정책을 지키며 신청을 저장한다. |
| F05 | 수강취소 | 신청 관계를 제거한다. |
| F06 | 이번 학기 시간표 | 학생의 대상 학기 신청 강좌와 수업 시간을 반환한다. |
| F07 | GET /health | 데이터 준비 및 API 사용 가능 상태에서 HTTP 200을 반환한다. |

## 2. 불변식

| ID | 항상 유지해야 하는 조건 | 출처 |
|---|---|---|
| I01 | 개설 강좌의 신청 수는 정원을 초과하지 않는다. | 원 과제 |
| I02 | 학생의 같은 연도·학기 신청 학점 합은 18 이하이다. | 원 과제 |
| I03 | 학생의 같은 연도·학기 신청 강좌 수업 시간이 서로 겹치지 않는다. | 원 과제 |
| I04 | 같은 학생은 같은 개설 강좌에 중복 신청할 수 없다. | 추가 정책 |
| I05 | 같은 학생은 같은 연도·학기에 같은 과목의 여러 분반을 신청할 수 없다. | 추가 정책 |

이 조건들은 순차 요청뿐 아니라 동시 요청에도 유지되어야 한다. 검사와 저장을 각각 수행하는 것만으로는 보장되지 않는다. 구체적인 락·트랜잭션 경계·격리 수준·재시도 전략은 미정이다.

## 3. 확정 정책

| ID | 정책 | 근거·영향 |
|---|---|---|
| D01 | 학번은 유일하고 변경되지 않으며 학생 PK로 사용한다. | 학번의 유일성과 불변성을 도메인 전제로 둔다. |
| D02 | 학생은 학번 외에 이름·소속 학과·학년을 저장한다. 전화번호·생년월일은 제외한다. | 필요한 프로필만 유지한다. 학생 학과는 학생 소속을 나타내며, 학과별 강좌 조회는 강좌 학과를 사용한다. |
| D03 | 과목 코드로 과목을 구별한다. 개설 강좌는 특정 연도·학기의 분반이다. | 동일 과목의 다른 분반 중복을 판별한다. |
| D04 | 개설 강좌에 별도 PK를 두며, 강좌코드는 같은 연도·학기 안에서 유일하다. | 다음 학기에 강좌코드를 재사용할 수 있다. |
| D05 | 학기 테이블 없이 개설 강좌에 연도와 학기를 저장한다. | 현재는 학기 자체의 독립적인 관리 요구가 없다. |
| D06 | 서버 설정의 대상 연도·학기에 대해서만 신청한다. 이번 학기 시간표도 이 대상을 사용한다. | 날짜와 독립적으로 다음 학기 신청을 운영할 수 있다. 학점·과목 중복·시간 충돌 검사도 대상 학기 기준이다. |
| D07 | 이미 신청한 개설 강좌의 신청은 거절하고 이미 신청했다는 이유를 전달한다. | 요청 중복으로 신청·학점이 늘어나지 않는다. |
| D08 | 수업 종료 시각과 다음 수업 시작 시각이 같으면 함께 신청할 수 있다. | 시간 구간의 경계가 맞닿는 연속 수업을 허용한다. |
| D09 | 취소한 강좌에 재신청할 수 있다. | 재신청 당시 모든 조건을 다시 검사하며 자리를 예약해 두지 않는다. |
| D10 | 학생·강좌가 존재할 때 신청 내역이 없거나 이미 취소돼도 취소는 성공한다. | 클라이언트가 신청 상태를 먼저 구분할 필요가 없다. 존재하지 않는 학생·강좌의 응답은 미정이다. |
| D11 | 현재 신청만 저장하고 취소하면 수강신청 행을 삭제한다. 상태 컬럼과 취소 이력 정리 작업은 두지 않는다. | 취소 이력 보관 요구가 없어 현재 관계만 관리한다. 재신청은 새 관계 행을 추가한다. |
| D12 | 수업 시간은 별도 테이블에 요일·시작·종료 시각을 저장하고 개설 강좌와 1:N으로 연결한다. | 한 강좌의 복수 수업 시간을 표현한다. |
| D13 | 학과·교수를 별도 테이블로 둔다. 교수는 하나의 학과에 소속된다. | 소속 정보와 담당 관계를 구분한다. |
| D14 | 개설 강좌에 소속 학과를 연결하며 타 학과 교수도 담당할 수 있다. | 교수 소속과 강좌 개설 학과는 다른 사실이다. |
| D15 | 교수와 개설 강좌는 N:M이며 공동 강의를 허용한다. | 강의 담당 연결 테이블로 여러 교수를 표현한다. 원 과제에 추가한 정책이다. |
| D16 | 전체·학과별 강좌 목록은 서버 설정의 신청 대상 연도·학기만 조회한다. | 조회 범위와 신청 가능 학기를 일치시킨다. 클라이언트가 다른 학기를 선택하는 조회 기능은 제공하지 않는다. |
| D17 | 전체·학과별 강좌 목록은 페이지 번호 방식으로 제공한다. | 강좌 목록의 조회 방식과 예상 규모를 고려해 선택했다. 성능 검증은 후속 작업이며, 페이지 번호 시작값·정렬 기준·기본/최대 크기·전체 건수 제공 여부는 미정이다. |

### 상태 보관 결정의 변경

취소 상태를 저장하고 나중에 정리하는 방안과 취소 시 행을 삭제하는 방안을 비교했다. 취소 이력 보관 요구가 없으므로 상태 필터링·재활성화·정리 작업을 줄이는 D11을 선택했다. 성능 우위는 이 결정의 근거로 사용하지 않는다. 관련 입력은 프롬프트 6~8에 남아 있다.

### 시간 충돌의 표현

같은 요일의 수업 A와 B가 `A.start < B.end` 그리고 `B.start < A.end`이면 충돌한다. 반열린 구간 `[시작, 종료)`로 D08을 표현한 것이다. 서로 다른 요일은 충돌하지 않는다. 매주 반복하며 자정을 넘기지 않는 수업 범위는 검토 중인 제안이다.

## 4. 초기 데이터 및 제출 요구

원 과제 기준으로 학과 10개, 개설 강좌 500개, 학생 10,000명, 교수 100명 이상을 실행 시 생성한다. 현실적인 이름·패턴을 사용하고, 완성 레코드가 담긴 정적 SQL·CSV나 대량 리터럴로 대체하지 않는다. 소규모 이름 토큰은 사용할 수 있다. 데이터 생성과 헬스체크 준비는 시작 후 1분 이내이며 생성 결과도 비즈니스 규칙을 지켜야 한다.

빌드·실행법, 에이전트 지침, 실제 프롬프트 이력, 요구사항, 요청·응답·오류·예제를 포함한 API 문서가 필요하다. 현재는 설계 문서 단계이며 서버 실행법과 API 명세는 후속 작업이다.

아래는 실행 결과가 아닌 테스트 설계다. 오류 응답 후 불필요한 신청 행이 생기지 않는지도 확인한다.

| T01 | 다른 제한에 걸리지 않는 100명이 잔여 1석에 동시 신청 | 정확히 1건 성공, DB 신청 수가 정원과 일치 | I01 |
| T02 | 15학점 학생이 3학점 신청 / 별도 사례로 4학점 신청 | 각각 총 18학점 성공 / 19학점 거절 | I02 |
| T03 | 15학점 학생이 겹치지 않는 서로 다른 과목 3학점 강좌 둘에 동시 신청. 두 강좌 모두 정원 여유가 있고 다른 실패 조건은 없음 | 정확히 한 요청 성공·한 요청 거절, 신청 행 1개 추가, 최종 18학점 | I02 |

| T06 | 동일 강좌 순차·동시 중복 신청 | 신청 관계가 하나만 존재 | I04, D07 |
| T07 | 해당 과목을 미신청한 학생이 같은 학기의 시간 안 겹치는 두 분반에 순차·동시 신청(별도 사례). 정원·학점 등 다른 실패 조건은 없음 | 각 사례에서 정확히 한 요청 성공·한 요청 거절, 해당 과목의 신청 행 1개 | I05 |
| T08 | 동일 학생이 서로 다른 과목의 시간 충돌 강좌 둘에 동시 신청. 각 강좌는 기존 시간표와 충돌하지 않고 정원·학점 등 다른 실패 조건은 없음 | 정확히 한 요청 성공·한 요청 거절, 신청 행 1개 추가, 최종 시간표 충돌 없음 | I03 |

| T10 | 취소 후 재신청 / 그 사이 정원이 찬 경우 | 조건 만족 시 성공 / 정원 부족 시 거절 | D09 |
| T11 | 다른 연도·학기 강좌 신청 | 거절, 기존 데이터 변화 없음 | D06 |
| T12 | 다른 학기에도 신청 내역이 존재 | 학점·시간표·동일 과목 검사에서 다른 학기 제외 | D06 |
| T13 | 신청과 취소가 겹침 | 허용 가능한 처리 순서에 부합하며 최종 관계·인원·학점 일치 | I01~I05 |
| T14 | 타 학과 교수 둘이 한 강좌 담당 | 관계 저장·조회 가능, 동일 담당 관계 중복 불가 | D14, D15 |
| T15 | 초기 데이터 생성·헬스체크 | 최소 규모·정합성 충족, 1분 내 준비 완료 | 원 과제 |
| T16 | 여러 연도·학기에 강좌가 존재할 때 전체·학과별 목록 조회 | 설정된 대상 학기 강좌만 반환하며 학과 조건도 함께 적용 | D16 |

동시성 검증은 성공 응답 개수뿐 아니라 커밋 후 DB 상태도 확인한다. T13의 응답 의미와 취소·재신청 경합은 트랜잭션 설계 때 구체화한다. 한 번의 성공 실험만으로 모든 실행 순서의 정합성을 주장하지 않는다.

## 6. 미정 사항과 후속 설계 순서

| 순서 | 아직 결정하지 않은 내용 |
|---|---|
| 1 | 취소도 대상 학기로 제한할지, 대상 설정 누락·오류·변경 시 처리 |
| 2 | 학기 허용 값(계절학기 포함 여부), 학년·학점 범위, 매주 반복/자정 초과 수업 지원 여부 |
| 3 | 과목명과 개설 강좌명의 분리 필요성, 물리 타입·PK 생성 방식, 최소 담당 교수·수업 시간 수 |
| 4 | 신청자 식별 및 인증, 없는 학생·강좌 처리, HTTP 경로·상태 코드·오류 우선순위, 페이지 번호 시작값·정렬·기본/최대 크기·전체 건수 제공 여부 |
| 5 | DB·기술 버전, 데이터 생성·재시작 정책, 트랜잭션 경계·잠금 순서·격리 수준·재시도 |
| 6 | 현재 인원 계산 방식, 교수 시간 충돌 검사, 신청 날짜·시간 및 학년별 제한의 구현 여부 |

신청 기간·학년별 시간 제한은 미정이다. 공동 강의의 담당 요일·대표 교수·기여율도 후속 요구사항 검토 대상으로 둔다.
