# 정원 30명 경쟁 검증과 부하 계측

## 변경 의도

정원 30명인 빈 강좌에 서로 다른 학생 200명이 한 번씩 신청했을 때 HTTP 성공과 DB 저장 인원을 함께 검증한다. 취소·반복 신청이 있는 기존 기준값 시나리오와 구분한다. 이어서 100명 집중·분산·조회 혼합 부하에서 연결 풀·DB 잠금·쿼리·자원 사용을 관찰한다. 업무 로직, 학생 → 강좌 잠금 순서, 3초 잠금 대기, 연결 풀 크기는 변경하지 않는다.

## 계측 구성

Spring Boot BOM으로 Actuator 4.1.1과 Micrometer Prometheus 1.17.1을 사용한다. 기존 HikariCP는 7.0.2다. 기본 실행은 Actuator 접근·지표·Prometheus 내보내기를 끈다. diagnostics 프로필에서만 지표 수집과 Prometheus 읽기를 켠다. 관리 서버는 127.0.0.1의 별도 포트에 바인딩하며 기존 JWT 인증을 적용한다. 업무 포트 지표 404, 관리 포트 무인증 401, 인증 후 200을 실행 스크립트에서 검사한다. 진단 프로필은 임시 측정 환경용이다.

- Hikari active/pending/max와 acquire/usage 타이머: 사용 중 연결 수, 연결을 기다리는 스레드 수, 연결 획득·점유 시간. 누적 타이머 차이로 측정 구간 평균을 계산한다. HTTP 지연과 1:1로 대응하는 요청 추적 값은 아니다.
- PostgreSQL pg_stat_activity와 pg_blocking_pids: 샘플 시점의 대기 유형·차단 관계. query_age_ms는 쿼리 시작 이후 시간이며 순수 잠금 대기 시간으로 해석하지 않는다. 짧은 대기는 샘플 사이에서 누락될 수 있다.
- pg_stat_statements: 본 측정 직전 초기화하고 종료 후 호출 수·총/평균/최대 실행시간을 저장한다. 쿼리 시간에는 실행 중 발생한 잠금 대기도 포함될 수 있으므로 CPU 연산시간으로 해석하지 않는다.
- JVM 프로세스 CPU·메모리는 Micrometer, PostgreSQL·k6 자원은 Docker stats로 관측한다. Docker CPU 백분율은 코어 1개 사용이 100%인 값이며 JVM의 전체 가용 CPU 기준 비율과 직접 비교하지 않는다.

수집기는 별도 프로세스로 실행된다. 각 샘플 후 1초 쉬며 Docker 자원 수집은 더 낮은 빈도로 한다. 실제 간격은 수집 소요 시간만큼 늘어나므로 시작·종료 UTC 시각을 함께 기록한다. SQL·자원 수집에도 비용이 있으며 계측을 끈 실행과 비교한다. 모니터링 토큰은 인자로 전달하되 파일·결과·로그에 기록하지 않는다. 부하용 임시 토큰 파일은 finally에서 삭제한다.

## 재현

~~~powershell
./gradlew.bat test bootJar --no-daemon
# 200명 단발 신청 및 계측을 끈 비교 실행
./scripts/verify-initial-data.ps1 -FirstOnly -ApiSmoke -CapacityCheck -LoadBaseline -LoadUsers 100
# 동일 JAR에 계측을 켠 실행
./scripts/verify-initial-data.ps1 -FirstOnly -ApiSmoke -LoadBaseline -Diagnostics -LoadUsers 100
~~~

200명 k6 검증은 per-vu-iterations(200 VU, 사용자당 1회)이며 신청 후 취소하지 않는다. 정확히 같은 순간의 도착은 보장하지 않는다. 통합 테스트는 출발 장벽으로 200개 HTTP 호출을 함께 풀고 별도로 검증한다. 두 시험 모두 성공 30·COURSE_FULL 170·DB 행 및 고유 학생 30을 요구한다. 실패를 감추기 위한 재시도는 없다.

성능 비교는 동일 장비·동일 JAR, 조건별 준비 10초·측정 30초이며 계측 OFF → ON 순서다. 순서 효과·환경 편차가 있어 작은 차이를 계측의 순수 비용으로 단정하지 않는다. 각 실행의 원본은 출력된 RESULT_PATH 디렉터리에 저장한다.

### 판단과 한계

- **확인:** 집중 부하에서는 강좌 잠금 경쟁과 DB 연결 확보 대기가 함께 나타났다. 분산 부하에서도 연결 확보 대기가 발생했으며 강좌 잠금 SQL 자체의 평균 실행시간은 짧았다. 강좌 잠금만으로 전체 지연을 설명할 수 없다.
- **환경:** 세 조건 모두 시스템 CPU 사용률이 100%에 이른 샘플이 있었다. JVM 프로세스 CPU 최대는 각각 약 28.95%·18.64%·27.11%(전체 가용 CPU 기준)였다. JVM 힙 사용량 최대는 약 123.82·114.49·127.92MiB였다. 이 샘플만으로 CPU 사용 주체 전체나 메모리 병목 여부를 확정하지 않는다.
- **계측 비용:** ON 실행은 OFF보다 느렸다. 특히 집중 p95가 2.86초에서 6.99초로 달라졌다. 계측 외에 실행 순서·장비 부하 편차도 섞여 있으므로 이 차이 전체를 Actuator나 수집기의 비용으로 해석하지 않는다. 이번 ON 수치를 기존 일반 실행의 성능 보장으로 사용하지 않는다.
- **후속:** 다른 작업 부하를 통제하거나 서버·부하 생성기를 분리한 조건에서 반복 확인한다. 그 뒤 연결 점유 구간을 더 세분화하고 연결 풀 크기 또는 잠금 방식을 바꿀 필요가 있는지 판단한다. 대기자가 있다는 이유만으로 풀 크기를 늘리면 DB 경쟁을 키울 수 있으므로 이번에는 설정을 변경하지 않았다.

실제 JAR에서 기본 실행의 지표 404와 진단 실행의 업무 포트 404·관리 포트 무인증 401·인증 후 200을 확인했다. 두 정상 비교 실행 모두 API smoke가 통과했다. 진단 수집기 개발 중 JSON 여러 줄 처리 오류로 중단한 실행과 짧은 확인 실행은 위 결과에 합산하지 않았다. 측정과 Gradle 테스트는 동시에 실행하지 않았다.

## 반복 측정과 Windows 호스트 계측

후속 반복은 같은 JAR·DB 데이터·100명 조건·잠금/연결 풀 설정을 유지한다. Windows GetSystemTimes의 idle·kernel·user 누적 시간 차이로 호스트 CPU를 별도 산출한다. kernel에는 idle이 포함되므로 CPU 사용 비율은 1 - idle차이/(kernel차이 + user차이)로 계산한다. 근거는 [Microsoft GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes)다. 현재 장비는 논리 프로세서 8개다.

서버 기동 전에 15초 관측하고 이후 5초 간격을 목표로 기록한다. 실제 간격에는 프로세스 조회 비용이 포함된다. 단계별 평균은 관측 간격으로 가중하고, 단계 시작/종료 이벤트 사이에 끝난 샘플을 집계한다. 경계의 샘플 일부는 직전 단계와 겹칠 수 있다. 고빈도 추적이나 순수 계측 비용 측정은 아니다.

프로세스별 CPU 차이와 이름은 원인 확인용으로 .tools의 로컬 기록에만 둔다. 공유 JSON에는 호스트 CPU 집계만 포함한다. 다른 프로그램을 임의로 종료하거나 전원·Docker 자원·풀 크기를 변경하지 않는다. 부하 전 관측이 낮더라도 시험 전체가 격리됐다는 뜻은 아니다. 별도 장비의 k6 실행은 이번에 수행하지 않는다.

~~~powershell
./scripts/verify-initial-data.ps1 -FirstOnly -ApiSmoke -LoadBaseline -Diagnostics -HostDiagnostics -LoadUsers 100
./scripts/summarize-load-diagnostics.ps1 -RunDirectory <RESULT_PATH의_디렉터리>
./scripts/summarize-host-load.ps1 -RunDirectory <RESULT_PATH의_디렉터리>
~~~
