# API·동시성·기술 설계 결정 정리

## 1. 목록 조회와 페이지

> 강좌 목록은 서버에 설정된 신청 대상 학기만 조회할 수 있도록 하겠습니다. 조회 방식과 규모를 생각하면 페이지 번호 방식으로 진행해도 무리가 없을 것 같습니다. 강좌명 → 개설 강좌 ID 오름차순으로 정렬하겠습니다.

> 페이지는 제안한 대로 0부터 시작하고 기본 크기 20, 최대 100으로 하겠습니다. 페이지 응답 구조와 생략 시 기본값, 빈 목록 처리도 제안한 기준으로 통일하겠습니다.

## 2. 강좌 응답과 입력 오류

> 개설 강좌 ID, 강좌명, 학점, 정원, 현재 인원, 수업 시간, 학과, 교수를 반환하겠습니다. 수업 시간에는 요일과 시작·종료 시각을 넣겠습니다. 영문 필드명과 요일·시간 표기는 제안한 형식으로 하겠습니다.

> 파라미터 선에서 먼저 처리하면 DB에 접근하지 않을 수 있으니 입력 검사를 먼저 하겠습니다. 정상 조회는 200, 잘못된 파라미터는 400, 존재하지 않는 학과는 404로 하겠습니다. 세부 검사 순서와 오류 코드·메시지는 제안한 기준으로 통일하겠습니다.

관련 명세: [강좌 목록 API](../docs/API.md)

## 3. 학생·교수 목록

> 학생 목록은 학과와 학년을 조건으로 조회할 수 있도록 하겠습니다. 학년은 1~4학년으로 한정하겠습니다. 교수 목록에도 학과 필터를 적용하고 페이지 구조는 동일하게 하겠습니다.

> 목록의 학과 정보는 학과명으로 통일하겠습니다. 학생은 학번 순, 교수는 ID 순으로 정렬하고 나머지 응답과 오류 처리는 제안한 기준으로 진행하겠습니다.

관련 명세: [학생 목록 API](../docs/STUDENTS_API.md), [교수 목록 API](../docs/PROFESSORS_API.md)

## 4. 계정 준비와 로그인

> ID와 비밀번호를 사용하고, ID는 학번으로 하겠습니다. 학생 생성 시 학번에 따른 로그인 계정을 준비하겠습니다.

> 초기 설정은 학생의 이메일로 일정 기간만 사용할 수 있는 임시 비밀번호를 전송하고, 최초 로그인 시 비밀번호를 설정하는 방식으로 하겠습니다. 이번에는 비밀번호 설정 과정을 모의 처리하여 초기 학생 데이터에 임의의 비밀번호를 부여하겠습니다.

> API는 POST /auth/login, 학번은 숫자, 비밀번호는 문자열로 하겠습니다. 응답으로 JWT를 받고 Bearer 방식으로 사용하겠습니다. 필수 값 누락은 400, 학번 또는 비밀번호 불일치는 401로 응답하겠습니다. 성공 응답과 세부 입력 검증은 제안한 기준으로 하겠습니다.

관련 명세: [로그인 API](../docs/AUTH_API.md)

## 5. JWT와 인증 범위

> JWT에는 학번, 발급자, 토큰 사용 대상, 발급 시각, 만료 시각을 담겠습니다. 유효기간은 발급 후 30분으로 하고 만료 이후에는 재로그인하도록 하겠습니다. 만료 전 재발급 요청은 가능하게 하되 세부 정책은 나중에 결정하겠습니다.

> 시간 기준은 KST로 하겠습니다. 학생·교수 정보와 강좌 목록은 로그인했을 때만 조회할 수 있도록 하겠습니다. 수강신청·취소·시간표 조회는 JWT의 sub로 학생을 식별하고, 토큰 누락·위조·만료는 모두 401로 처리하겠습니다.

> 로그인하여 토큰이 발급된 학생이 삭제되는 상황은 고려하지 않겠습니다. 별도의 학생 존재 확인은 신청 처리 과정에서 제외하겠습니다.

## 6. 수강신청 요청과 오류

> 신청 요청에는 제안한 대로 개설 강좌 ID를 받고, 학생은 토큰으로 식별하겠습니다. 성공 응답은 201로 하겠습니다.

> 잘못된 요청값, 존재하지 않는 강좌, 신청 대상 학기가 아닌 강좌는 각각 400, 404, 409로 처리하겠습니다. 메시지는 "잘못된 요청입니다.", "존재하지 않는 강좌입니다.", "신청 대상 학기가 아닙니다."로 하겠습니다. 입력 값은 정수로 제한하겠습니다.

> 인증 → 입력 검증 → 개설 강좌 존재 확인 → 대상 학기 확인 → 신청 조건 검사 순서로 처리하겠습니다. 세부 입력 검증과 오류 코드는 제안한 기준으로 하겠습니다.

관련 명세: [수강신청 API](../docs/ENROLLMENTS_API.md)

## 7. 신청 조건과 잠금

> 동일 강좌인지 먼저 검사하고, 그다음 동일 과목인지 검사하겠습니다. 동일 강좌라면 이미 신청한 강좌임을 알리고 동일 과목이라면 중복 과목임을 알리겠습니다.

> 여러 학생이 같은 강좌를 신청하면 강좌 잠금을 두고 경쟁할 수 있습니다. 학생 조건 위반으로 실패할 요청이 강좌 잠금을 점유하는 것을 피하기 위해 중복 신청, 최대 학점, 시간표 충돌을 먼저 검사하겠습니다. 이 조건을 통과한 요청만 강좌 잠금을 획득해서 정원을 검사하겠습니다.

> 학생 조건은 학생 행 잠금으로 보호하겠습니다. 격리 수준은 READ COMMITTED로 하고 잠금을 획득한 후 조회하여 커밋을 반영하겠습니다. 강좌의 현재 인원은 신청 테이블의 COUNT로 확인하겠습니다. 조건 위반의 응답은 제안한 409와 오류 코드·메시지로 통일하겠습니다.

## 8. 취소·시간표와 잠금 실패

> 취소는 신청 대상 학기로 제한하고, 신청과 같은 학생 → 강좌 순서로 잠금을 잡겠습니다. 시간표는 수강신청한 순서로 반환하겠습니다. 신청 테이블에 증가 ID를 부여해서 성공한 신청 순서를 표현하겠습니다.

> 취소의 204 응답과 페이지 없는 시간표 응답은 제안한 구조로 하겠습니다. 잠금 대기는 제안한 3초로 시작하고, 대기 시간 초과나 교착 오류는 전체 롤백 후 503으로 처리하겠습니다. 자동 재시도는 지금은 하지 않고 이후 검토할 사항으로 남기겠습니다. 신청 처리 중 강좌 정보 변경은 지원하지 않겠습니다.

관련 명세: [취소](../docs/CANCELLATIONS_API.md), [시간표](../docs/TIMETABLE_API.md), [동시성 설계](../docs/CONCURRENCY_DESIGN.md)

## 9. 기술 스택과 매핑 방침

> JPA를 사용하고, 나머지 기술 스택은 추천한 구성으로 진행하겠습니다. 잠금은 JPA로 먼저 적용하고 원하는 잠금이 걸리는지 확인한 뒤, 필요하면 native query를 쓰는 방식으로 하겠습니다.

> 학기는 계절학기를 제외한 1·2학기만 지원하겠습니다. 나머지 키·제약조건과 JPA 매핑은 제안한 기준으로 진행하겠습니다.

채택한 구성과 세부 방침: [기술 스택·물리 모델](../docs/TECH_STACK_PROPOSAL.md), [요구사항 D73~D78](../docs/REQUIREMENTS.md)
